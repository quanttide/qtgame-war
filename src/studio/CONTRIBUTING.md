# CONTRIBUTING

## ROADMAP 的定位：工作记忆

[ROADMAP.md](ROADMAP.md) 是本仓的工作记忆，不是设计文档，也不是归档文档。三条定位：

- **随工作变化动态调整**：开工前读一遍；任务拆细、顺序调整、状态勾选、新发现的坑，随手改进去。工作记忆的价值在于此刻准确，不在于写得完整。做完的事勾掉并留在原位，不必移到别处归档。
- **只记近端**：当前版本（v0.1.x）的细分任务在这里；跨版本的方向与阶段目标在主仓 `data/roadmap/qtgame-war/`；设计共识（核心机制为什么成立、架构约束、核心/剧本边界清单）在创始人档案仓 `qtgame-war/` 分区。三层各管一段，本文件不复制另两层的内容。
- **和长期记忆互动**：工作里冒出的原则性结论——不是「这个任务做完了」，而是「以后都该这样」——上升到长期记忆。具体去向：
  - 版本目标、验收标准、阶段顺序的变化 → 改主仓 `data/roadmap/qtgame-war/` 对应版本文件
  - 核心机制、架构约束、边界划分的变化 → 改创始人档案仓 `qtgame-war/` 分区
  - 模块的接口与规格 → 改本目录 `doc/models/`

上升之后，ROADMAP 里的对应条目同步改，不留两份冲突的表述。

## 提交

- 遵循 Conventional Commits，用中文描述（见主仓 git-commit skill）
- 提交信息避开禁用词：证据、判据、判定、张力、产物、落点、依据、口径
- 变更一律提交并推送，子模块指针在父仓逐层更新

## 测试与交付

- 测试框架 flutter_test，用中文描述；用内存构造 `CampaignConfig`，不走 rootBundle
- 每次交付按 doc → test → lib 三件套：先改 `doc/models/` 规格，再写测试，最后实现
- `resolveCombat` 等结算函数是随机的：测试断言结构与边界，不断言具体数值
- 签名或结构性改动后，用 grep 复核文件真实内容再跑测试

## 代码约束

- 核心代码检索不到剧本专名（帝丘店、龙王店、华野、playerPower 等），验收覆盖 JSON schema，不只 Dart 代码
- 红蓝语义：`Side.blue` = 华野 = 玩家方，`Side.red` = 国军；与原型和中文战棋惯例相反，移植时显式核对敌我
- 剧本注入优先：新功能先问归核心还是归剧本，判断表见档案仓 `qtgame-war/constraints.md`；不为核心打剧本补丁
