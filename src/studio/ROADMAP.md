## v0.0.2 — 可赢可读（帝丘店成局）（已完成，2026-10-29）

**前置**：v0.0.1 已固定——本版不动引擎（守卫/原语/schema 归 v0.0.4），只修剧本数据、反馈出口与决策语义。

**目标**：把「能打完」升级成「能赢、看得懂」——赢的路接通，每次点击有可读的变化。

**验收**：整局 bot 种子批至少一次胜（占领或歼灭均算）；人下一局能从事件条读出每次决策的结果；三张决策卡行为各异。

**核实**（2026-10-29 走查取证，落地时修正一处误判）：
- 整局 bot 实跑结局 = 第 13 回合超时判负（插桩输出 `victory=false turn=13`）——「打完」绿而「能赢」无路
- 要塞格上其实一直有人：`units.json` id 20「整25师40旅(核心)」在 (5,4)，21/22 侧翼；四支援军也在 campaign.json——但全部红方缺 `revealed` 字段 → 默认 false → **幻影：不可被攻击、自己也不行动**（初次诊断误判为「无人落位」，系 grep 只匹配了带 `revealed` 的行）。对玩家等于空城，工事永远降不了，占领胜利死路
- `translateOrders` 攻城线目标 = 要塞格 → 决策卡把兵带向空城，不主动索敌；AI 会打玩家 → 被动磨到超时
- 战报读出通道随战况面板删除，反馈只剩地图上 6px 血点——玩家看不到变化，只能重复点
- 「强攻」与「围困」行为全同（两者同属 `assaultTargets`、目标都是要塞，疲劳未接线），三选一实为二选一

- [x] 要塞守军接通（实做与原计划不同）：不加新单位——现有防线（id 20/21/22）与四支援军补显形（加 `revealed: true`）+ `initial_fort_strength` 3→1（一格一站位，守军阵亡只减一次，3 是不可达的死数字）——验收：工事可降、占领可达（实测最快 T3 占领）；强攻卡有真实攻防对象
- [x] 事件条：地图下方一行最新事件（取 `state.logMessages` 尾条 `.msg`）——验收：下达决策与每次交战后该行立即更新，玩家能读出「刚才谁干了什么、结果如何」
- [x] 决策卡去重 + 阻援接线：「围困」换「阻击援军」（阻援线实为 `TaskType.reliefTasks={block,flank,lure}`，卡用 `block`），`reliefPos` 从写死 null 改为首支存活援军位置，未到则 null（原地待命）——验收：三卡行为各异；第 7/8 回合援军到达后阻击卡指向援军
- [x] 整局测试升种子批：12 个固定种子跑强攻 bot，断言至少一胜——验收：实测 **8 胜 4 败**（胜 T3–T6 占领要塞，败 T13 超时），全败时变红（`test/integration/full_game_test.dart`；附带坑：同测试进程第二次 `CampaignConfig.load` 永久挂起，且跨 testWidgets await 缓存 Future 也挂——缓存解析后的值本身）
- [x] 验收纪律入册：跨版本纪律已新增「每版验收必含『至少一条赢的路可达』」——验收：纪律节有此行，其后每版验收对查

## v0.0.3 — 指挥界面认知改版（开工 2026-10-29）

**来源**：实机走查 + 设计评审——13 点问题清单（信息层级混乱 / 反馈与可供性缺失 / 视觉语言不统一）+ 根因分析 + 5 个优先方向，全文归档本次评审记录。

**根因（评审结论，与本文件「整体成立没有属主」同病）**：界面按代码结构摆放（顶=元数据、右=命令枚举、底=日志、中=棋盘），而非指挥官决策流（看态势→选单位→评估→下令→看反馈）；UI 被当渲染层而非认知工具；无设计系统，色彩语义各自为政。

**核实注记（2026-10-29 对照代码）**：

- #4「回合 2/1」代码上产生不了：渲染为 `回合 {currentTurn} / {maxTurns}`，`campaign.json` `max_turns: 12`——待截图复核（疑为 "2 / 12" 误读或布局裁剪）

## 跨版本纪律

- 核心检索不到剧本专名（含 JSON schema），每版验收都查
- 每版验收必含「至少一条赢的路可达」——bot 种子批胜一次；机制绿而赢不了路的版本不算完成（v0.0.1 实战教训：整局测试绿但实为超时判负）
- 状态事实单一属主：新增全局状态（标志、评估时机、文案）先定归属再落字段；要写第二处时改派生，不改复制（任务 2 复盘根因）
- v0.2.0 起确定性常青：同种子双跑零偏离，不过即回滚（基线见主仓 `v0.2.0.md`）——比对范围须含 `GameController` 层 rng 消耗顺序，不只 `resolveCombat` 叶子函数
- 大模型不进结算，只碰文本层
- 红方 `hasActed` 现无代码读取；将来 AI 按 `hasActed` 做闸门须在回合末重置红方
