# 意图系统 — 设计洞察

> 记录设计意图系统过程中的关键认知转折，供未来回顾。

---

## 1. 原型做错了什么

第一个 HTML 原型是"选意图"的。三个按钮，点一个锁定，其他禁用。表面看起来合理——"你选了立场就不能反悔"。

但粟裕在豫东战役里改了四次意图。现实中的指挥官不是做一次选择就锁死的。

更根本的问题是：**玩家点按钮选意图这个交互本身就不对。** 指挥官不会坐在指挥所里说"让我选一下我的意图是什么"。他面对的是情报，他做判断，判断中自然包含立场。意图应该是判断的副产品，不是操作入口。

这是原型阶段最大的认知转折：不要把意图做成选择题，要做成系统对玩家判断的反馈。

## 2. "切换有代价"想对了，但想浅了

"意图可切换，切换消耗 +1"是对的——改变决心确实有成本。但原型里的消耗只是一个抽象数字。

消耗不应该是"扣点数"，它应该体现在游戏世界的具体变化里：切换意图后，时间推进了一格；部队刚准备出发又要停下来等新命令；正在传递中的旧情报可能在切换后失去价值。

**抽象消耗和具体消耗的区别，就是"游戏机制"和"模拟现实"的区别。**

## 3. "锁定"像一个约定俗成的设计陷阱

QA 文档最初写的是"意图按钮锁定不可改"，我照抄了，没有质疑。回头看，这是从传统策略游戏的"选择不可逆"习惯里带出来的——技能树点了不能洗、外交选项选了不能改。但指挥官决策游戏要模拟的是人在不确定中做决定，不是人在菜单里做配置。

被纠正后才意识到：好的设计约束不是"你不能改"，而是"你可以改，但你要承担改的后果"。

## 4. 战役预设初始意图是对的，但不够

每个战役开局指定一个初始意图（帝丘店→积极防御，开封→保护平民），这个做法的核心洞察是：**指挥官到任的时候，战场已经告诉他该做什么了。**

但现在的原型只是把初始意图作为一个默认值写在 JSON 里，玩家看到的是标签高亮了，没有让玩家感受到"这个局势在推着我往这个方向走"。

理想的做法应该是：开局展示情报和局势（不展示意图标签），玩家通过做第一个决策来表达意图，系统再反馈"你的决策表明你的意图是积极防御"。这样意图是玩家自己"长出来的"，不是系统预设的。

## 5. 这个系统应该多晚才算完成

意图系统不是独立的——它必须等情报系统（Phase 2.1）上线后才能体现价值。没有情报迷雾，玩家直接能看到战场全貌，意图就是个多余的标签选择器。有了情报迷雾，玩家面对不确定的信息做出判断，这个判断投射为意图才有分量。

这也是为什么 Phase 2 先做情报系统再做意图系统——不是编码顺序问题，是**设计上意图依赖情报才成立**。

## 6. 设计文档分层的价值

这次做完 intent 系统后同步创建了 `docs/intention/`（概念层）和 `docs/brochure/`（玩家层），并明确了分层纪律。

回头看，如果没有这个区分，intention 里写的理想设计就会被当作"现状"或"已实现功能"被误引用。brochure 里的玩家说明也会被当作设计规范来要求实现。分层不是形式主义——它防止了"文档描述的状态和实际代码状态脱节"这个之前踩过的坑。

## 7. LLM 验证揭示了映射规则的边界

用 Python 脚本调用 LLM 模拟指挥官判断，9 个场景 7/9 匹配预设意图。

三个基准场景（帝丘店、开封、豫东第一阶段）全部匹配，验证了"情报→判断→意图"映射规则的基础成立。

两个不匹配案例暴露了更有价值的信息：

**矛盾情报场景**（预设为"积极防御"）：
LLM 选了"收集情报"——理由是两份情报互相矛盾，贸然防御可能分散兵力，先核实再说。这个判断比预设更合理。

**多重压力抉择场景**（预设为"积极防御"）：
LLM 同样选了"收集情报"——理由是侦察兵失联、敌主力位置不明，贸然分兵可能中计。

共同规律：**当 LLM 认为信息不足以支持决策时，它倾向于退回"收集情报"作为默认退路。** 这不是映射规则错误，而是暴露了预设意图的盲区——预设意图假设玩家在已知信息下做最优选择，但"信息本身是否足够做决策"这个前提没有被预设意图机制考虑。

这对设计的启示是：**意图系统不应该只有正向映射（情报→意图），还应该有一条反向保护规则：当情报质量低于阈值时，默认意图应该是"收集情报"而非保持原预设。**

这也印证了第 5 条的结论——意图依赖情报才成立。没有可靠的情报，任何意图都是空中楼阁。

## 8. LLM 实验对游戏设计意图的帮助

这个实验的价值不在"验证结果正确"，而在验证过程本身揭示了几个设计方向。

**8.1 确认了"意图从情报中自然生长"是可行的**

LLM 不需要任何规则表、映射表，仅凭情报文本就能输出与预设一致的意图。这意味着游戏中的"情报→意图"映射不依赖硬编码规则——只要给玩家足够好、足够情境化的情报文本，他的判断自然会落在一个意图上。

这对开发的影响是：**不需要为每个战役手写"情报→意图"映射规则。** 情报文本写到位了，意图自然成立。

**8.2 暴露了"预设初始意图"的局限**

两个不匹配案例的共同点是"情报质量低→LLM 退回收集情报"。对应的游戏设计问题是：

如果帝丘店开局给玩家的情报是模糊的、矛盾的，系统却把他的意图标为"积极防御"，玩家会感到违和——"我明明想先搞清楚状况"。

结论是：**初始意图不应该是 campaign.json 里写死的默认值，而应该是情报质量的产物。** 情报清晰时按战役逻辑预设，情报模糊时默认应该是"收集情报"。

**8.3 改变了"初始意图"的实现思路**

修改前：
```
campaign.json 写 initial_intent: "defend"
→ 玩家开局看到高亮的"积极防御"标签
```

修改后：
```
情报系统输出 → 根据情报质量计算初始意图 → 反馈给玩家
```

初始意图不再是一个配置字段，而是情报系统的输出。玩家看到的不再是系统强加的标签，而是"基于当前情报，系统认为你的立场是..."——更像参谋在说话，不是配置文件在生效。

**8.4 一个必须面对的矛盾**

这个验证方式本身恰好是"理想状态的反面"——我们用 LLM 模拟了完美指挥官，但游戏中不可能内置一个 LLM 来实时推断玩家意图。玩家是人，不是 LLM。

所以这个实验验证的不是"可以用 AI 替代意图系统"，而是**"情报→意图的映射在理论上是自然的"**——这给了我们信心：方向是做情报系统让玩家自己判断，而不是做意图按钮让玩家选择。

换言之，实验告诉我们不要做什么：不要做意图选择器（"请选你的立场"）。
实验也告诉我们做什么：做好情报系统（"这是当前战况，你决定怎么办"）。
