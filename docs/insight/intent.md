# 意图系统 — 设计洞察

> 记录设计意图系统过程中的关键认知转折，供未来回顾。

---

## 1. 原型做错了什么

第一个 HTML 原型是"选意图"的。三个按钮，点一个锁定，其他禁用。表面看起来合理——"你选了立场就不能反悔"。

但粟裕在豫东战役里改了四次意图。现实中的指挥官不是做一次选择就锁死的。

更根本的问题是：**玩家点按钮选意图这个交互本身就不对。** 指挥官不会坐在指挥所里说"让我选一下我的意图是什么"。他面对的是情报，他做判断，判断中自然包含立场。意图应该是判断的副产品，不是操作入口。

这是原型阶段最大的认知转折：不要把意图做成选择题，要做成系统对玩家判断的反馈。

## 2. "切换有代价"想对了，但想浅了

"意图可切换，切换消耗 +1"是对的——改变决心确实有成本。但原型里的消耗只是一个抽象数字。

消耗不应该是"扣点数"，它应该体现在游戏世界的具体变化里：切换意图后，时间推进了一格；部队刚准备出发又要停下来等新命令；正在传递中的旧情报可能在切换后失去价值。

**抽象消耗和具体消耗的区别，就是"游戏机制"和"模拟现实"的区别。**

## 3. "锁定"像一个约定俗成的设计陷阱

QA 文档最初写的是"意图按钮锁定不可改"，我照抄了，没有质疑。回头看，这是从传统策略游戏的"选择不可逆"习惯里带出来的——技能树点了不能洗、外交选项选了不能改。但指挥官决策游戏要模拟的是人在不确定中做决定，不是人在菜单里做配置。

被纠正后才意识到：好的设计约束不是"你不能改"，而是"你可以改，但你要承担改的后果"。

## 4. 战役预设初始意图是对的，但不够

每个战役开局指定一个初始意图（帝丘店→积极防御，开封→保护平民），这个做法的核心洞察是：**指挥官到任的时候，战场已经告诉他该做什么了。**

但现在的原型只是把初始意图作为一个默认值写在 JSON 里，玩家看到的是标签高亮了，没有让玩家感受到"这个局势在推着我往这个方向走"。

理想的做法应该是：开局展示情报和局势（不展示意图标签），玩家通过做第一个决策来表达意图，系统再反馈"你的决策表明你的意图是积极防御"。这样意图是玩家自己"长出来的"，不是系统预设的。

## 5. 这个系统应该多晚才算完成

意图系统不是独立的——它必须等情报系统（Phase 2.1）上线后才能体现价值。没有情报迷雾，玩家直接能看到战场全貌，意图就是个多余的标签选择器。有了情报迷雾，玩家面对不确定的信息做出判断，这个判断投射为意图才有分量。

这也是为什么 Phase 2 先做情报系统再做意图系统——不是编码顺序问题，是**设计上意图依赖情报才成立**。

## 6. 设计文档分层的价值

这次做完 intent 系统后同步创建了 `docs/intention/`（概念层）和 `docs/brochure/`（玩家层），并明确了分层纪律。

回头看，如果没有这个区分，intention 里写的理想设计就会被当作"现状"或"已实现功能"被误引用。brochure 里的玩家说明也会被当作设计规范来要求实现。分层不是形式主义——它防止了"文档描述的状态和实际代码状态脱节"这个之前踩过的坑。
